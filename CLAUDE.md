# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

`smithy` : TUI Rust (ratatui) pour consulter la CI de forges git. Forgejo et GitHub sont implémentés ; GitLab, Bitbucket et Azure DevOps sont prévus, d'où le trait `Provider`. Usage visé : machine sans bureau derrière un VPN. Outil personnel, publié sur GitHub (licence `MIT OR Apache-2.0`). L'UI et les messages sont en français.

## Commandes

Tout passe par le `Makefile` (qui ajoute `~/.cargo/bin` au `PATH`) ; `make` affiche l'aide.

- `make check` : `fmt-check` + `lint` (clippy `-D warnings`) + `test`, comme la CI. À lancer avant de conclure.
- Un seul test : `cargo test -p smithy-forgejo pagine_les_depots` (crate `smithy`, `smithy-forgejo` ou `smithy-core`) ; `cargo test -p smithy app::tests::` pour un module.
- `make dev-run` : démarre le Forgejo local si besoin, puis lance l'app dessus. `make run` utilise `SMITHY_URL`/`SMITHY_TOKEN` ou `~/.config/smithy/config.toml`. `smithy --fresh` ne rouvre pas les onglets sauvegardés ; `--version`, `--help` répondent sans config.
- `make release` : binaire glibc local. Le binaire distribué est un binaire musl statique construit par la CI (voir « CI et binaire Linux »).
- Couverture : `cargo llvm-cov --workspace` (non encadré par le Makefile). `main.rs` est à 0 %, le reste autour de 80–100 %.
- Rust ≥ 1.89 (`rust-version` du workspace) : verrou de fichier de la std (`File::try_lock`), chaînes de `let`.

## Architecture

Workspace de 4 crates, dépendances à sens unique : `smithy` → `smithy-forgejo` / `smithy-github` → `smithy-core`.

- **`smithy-core`** : modèles communs (`Repo`, `Pipeline`, `Status`, et pour l'explorateur et l'historique `Branch`/`BranchHead`, `Entry`, `EntryKind`, `FileContent`, `Commit`, `CommitPage`, `CommitDetail`), `Error`, `Capabilities`, trait `Provider` (méthodes `impl Future + Send`, pas `async_trait` : donc générique `P: Provider`, pas de `dyn`). Un nouveau backend (GitHub, GitLab…) = un nouveau crate qui implémente ce trait. `Capabilities` expose ce qu'un backend sait faire (ex. `logs`) pour que l'UI s'adapte. `Provider::job_log` a une implémentation par défaut `Unsupported` ; `clean_log_line` (ANSI, `\r`, tabulations) est dans le core pour que tous les backends rendent des lignes affichables ; `clean_text_line` sert aux fichiers (ne garde **pas** « ce qui suit le dernier `\r` » comme `clean_log_line`, qui ferait disparaître du contenu : les contrôles deviennent des images Unicode `␛`, `␍`…). `list_branches`, `read_dir`, `read_file` (plafond d'octets passé par l'appelant), `list_commits` et `commit_detail` ont une implémentation par défaut `Unsupported` ; `Capabilities.browse` les annonce.
- **`smithy-forgejo`** : client REST. Les champs serde sont tous `#[serde(default)]` sauf `id`, pour tolérer les écarts de version. Il traduit les statuts Forgejo (`waiting`, `blocked`, `success`, …) vers `Status`, et les codes HTTP vers `Error`.
- **`smithy`** (binaire) : l'état est **pur** et testé sans terminal ; seuls `main.rs` (boucle d'événements, un `tokio::spawn` par requête) et `ui.rs` (rendu ratatui, testé avec `TestBackend`) touchent au terminal.
  - `app.rs` : `App`, la **pile de pages** `App.stack: Vec<Page>` (`Home` au fond, jamais vide ; `Repo`, `Runs`, `Logs`, `Browser`, `Commits`, `Branches`, `Commit`), comme un navigateur : `Échap` dépile (`App::pop`) et retrouve la page d'avant telle quelle ; la page affichée est le sommet ; `App::breadcrumb()` donne le fil d'Ariane (une ligne en haut, ajusté à la largeur par `fit_breadcrumb`). Onglets, serveurs, login, instantané des onglets : voir les sections plus bas.
  - Pages : `pages.rs` (accueil, page d'un dépôt, runs et leurs filtres), `browser.rs` (explorateur de code, machine à états : dossier, sélecteur de branche, fichier, filtre par nom), `history.rs` (commits, branches, détail d'un commit et mise en forme du diff), `logview.rs` (le volet de texte `TextView` **partagé** par les logs, les fichiers, le Markdown rendu et les diffs : sections pliables, défilement en **lignes d'écran**, retour à la ligne, recherche ; index des lignes d'écran mis en cache par largeur ; `LogView` = `TextView` + dépôt + pipeline via `Deref`).
  - Texte : `wrap.rs` (découpage au caractère ou par mots avec retrait, `unicode-width`), `highlight.rs` (coloration syntaxique), `markdown.rs`, `textsearch.rs` (recherche, surbrillance).
  - Persistance (tout dans `~/.local/state/smithy/`, 0600) : `session.rs` (cookie + token issus du login, un fichier par serveur ; le mot de passe n'est jamais écrit), `recent.rs` (dépôts ouverts, références seulement), `workspace.rs` (onglets ouverts et verrou d'instance). `config.rs` : la config (serveurs multiples, `kind` + `url` + `token` optionnel, aucun secret hors token). `timeago.rs` : dates relatives sans dépendance.
  - **Flux** : l'état **dépose des `Request` dans une file** (`request.rs`) étiquetées du serveur de l'onglet (`App::take_tagged_requests`, aussi celles des explorateurs ouverts ; `requeue` remet celles dont le serveur n'a pas encore de fournisseur) que `main.rs` exécute (`run_request`) ; chaque réponse revient par canal sous forme de `Msg`, intégrée par `App::apply_for(serveur, msg)`. Les requêtes restent en file tant qu'il n'y a pas de fournisseur (connexion à faire) et partent dès que la connexion aboutit. Toutes les 5 s `App::tick` renouvelle ce qui change seul sur la page affichée (runs, logs d'un job en cours). Les réponses périmées (dépôt, branche, chemin, job ou page qui ont changé) sont ignorées par la page qui les reçoit.
  - **Vue des logs** (`w` retour à la ligne conservé par `App.logs_wrap` ; `Espace` plie la section courante, `→`/`←` la changent, `a` tout plier/déplier) : s'ouvre sur la première étape en échec ; un job en cours est rafraîchi toutes les 5 s et sa fin est suivie. Les étapes réussies ou ignorées démarrent repliées, comme sur le web ; l'état de pliage est gardé par indice d'étape, et une étape vue ouverte (elle tournait) le reste. La section courante est la sélectionnée avec les flèches droite/gauche, sinon celle de la ligne du haut : sans sélection explicite, un job tout replié qui tient à l'écran ne permettrait jamais d'atteindre la 2e étape.
  - **Session expirée** (`Error::SessionExpired`) : rouvre le formulaire de login du serveur concerné (seulement si c'est celui de l'onglet affiché), qui ne renouvelle alors que le cookie : créer un token à chaque expiration les ferait s'empiler sur le compte.

## Navigation et touches

- `Échap` ne quitte **jamais** : il dépile (sans effet à la racine). `q` quitte à la racine et dépile ailleurs ; `Ctrl+C` quitte partout. Le cadre d'une page ne répète pas ce que dit le fil d'Ariane (statut du job, chemin du dossier).
- **Pas de chiffres comme raccourcis** : sur AZERTY la rangée du haut donne `&é"'(` sans Maj. Pas non plus de `[ ] { }` (AltGr) ni de `Ctrl+T`/`Ctrl+W` (souvent pris par le terminal). Les onglets à venir se changeront avec `Tab`/`Maj+Tab`.
- Feuille de route décidée avec Thomas (2026-10-14) : 1) pile + fil d'Ariane (fait) ; 2) page d'accueil (fait, voir « Accueil et page d'un dépôt ») (mes dépôts, suivis/étoilés, explorer par recherche, récents ; organisations et notifications demandent des droits de token en plus : `read:organization`, `read:notification`, `read:issue`, mesurés en 403 sans, 200 avec sur Forgejo 15 — à demander **à la demande**, jamais au login) puis page d'un dépôt qui regroupe CI, Code, PR, Runners ; 3) onglets = piles indépendantes (fait, voir « Onglets ») ; restauration des onglets au lancement (fait, voir « Onglets ») ; 4) plusieurs serveurs à la fois, un par onglet (fait, voir « Onglets ») ; 5) PR (fait, consultation seule, voir « Pull requests »), filtres `/`, recherche dans les logs, coloration syntaxique, Markdown, historique des commits et branches (fait) ; **reste** : notifications, runners (droits de token en plus), README du dépôt sur sa page, filtre des étapes d'un log.

## Versions de Forgejo : un adaptateur par famille

Les routes web des logs varient selon la version, donc `smithy-forgejo/src/version.rs` associe la version (`/api/v1/version`, mise en cache dans `Forgejo::decision`) à un adaptateur `Flavor` et à un niveau de support (`Support::{Full, Partial, Unsupported}`) :

| Version | Adaptateur | Logs | CSRF (cookie `_csrf` + en-tête) | Segment `attempt` | Login |
|---|---|---|---|---|---|
| 10, 11, 12 | `Legacy` | complet (sondé) | exigé | absent (404) | champ `_csrf`, échec en 303 vers `/user/login`, cookies `i_like_gitea` + `gitea_incredible` |
| 13 | `Transitional` | complet (sondé) | exigé | obligatoire (500 sans) | idem |
| 14 | `Modern` | complet (sondé) | plus exigé | obligatoire | pas de champ `_csrf`, échec en 303, mêmes cookies |
| 15 | `Modern` | complet (sondé) | non | obligatoire (réponse vide sans) | pas de champ `_csrf`, échec en **200**, cookies `session` + `persistent` |
| ≥ 16 | `Modern` supposé | partiel | | | |
| ≤ 9, Gitea | — | non supporté (`Error::UnsupportedVersion`, aucune requête web) | | | |

Deux interrupteurs indépendants expliquent tout : le CSRF (retiré en 14) et `attempt` (apparu en 13). Autres faits mesurés : `currentJob` s'appelle `detail` en 10–13 et `details` en 14–15 (`allAttempts` apparaît en 13) ; dès la 13 la page du run redirige (307) vers `…/jobs/0/attempt/1` (on la suit pour lire le jeton) ; **sans `attempt`, les 13 et 14 répondent 500** : le premier appel part donc de la tentative 1 pour toutes les versions qui utilisent les tentatives ; le cookie `gitea_incredible` (10–14) dure 31 jours ; une étape hors bornes donne 500 (HTML) partout. Le login ne dépend pas de la version : il lit le formulaire (avec ou sans `_csrf`) et considère comme un échec toute réponse qui n'est pas une redirection hors de `/user/login`.

Une version partielle est utilisée et `JobLog.notice` la signale (⚠ dans le cadre de la vue des logs). Pour valider ou ajouter une version : `FORGEJO_VERSION=N dev/dev.sh probe` (instance isolée, voir plus bas), lire le JSON, puis ajuster `decide` et, si le comportement est nouveau, ajouter une variante de `Flavor`. Les 10, 11 et 12 se comportent à l'identique ; la 13 puis la 14 changent chacune une chose. Ne jamais déduire d'un test sur la 15 que la 10 se comporte pareil : c'est l'instance réelle de Thomas (v10, migration prévue).

## Onglets

Un onglet est une pile de pages indépendante. `App.stack` est **toujours la pile de l'onglet affiché** (tout le code des pages en dépend) ; les piles des autres sont dans `App.tabs`, une case par onglet avec une pile vide à la place de l'affiché. `go_tab` échange les deux ; `stacks_of(serveur)` donne les piles des onglets d’un serveur.
- **`t` = dupliquer puis ouvrir** : `open_in_new_tab` copie toutes les pages de l'onglet (`Page::fork` ; un `Browser` copié **ne reprend pas ses requêtes en attente**, sinon la même demande partirait deux fois), insère la copie juste après l'actuel, puis y fait « Entrée » sur la sélection (accueil → dépôt, dépôt → CI/Code, runs → logs, dossier → entrée). Sans sélection à ouvrir (logs, fichier) c'est une simple copie. 10 onglets au plus (`MAX_TABS`).
- **Les réponses réseau sont diffusées à tous les onglets du serveur qui a répondu** (`apply_for`, voir « Étiquetage des requêtes ») : chaque page prend ce qui la concerne (même dépôt, chemin, job, recherche) et écarte le reste. C'est ce qui règle aussi les réponses périmées ; aucun identifiant d'onglet ni de page dans les requêtes, seulement le serveur. Corollaire : `smithy_core::Error` est `Clone`.
- **Onglets en arrière-plan** : pas de rafraîchissement, sauf un job en cours (`tick` redemande ses logs et la liste des runs) pour que le titre passe de `●` à `✔`/`✘` (`TabMarker`, calculé par `marker_of` depuis la page de logs et la liste des runs plus bas dans la pile). Pas de cloche.
- Touches : `Tab`/`Maj+Tab`, `t`, `x`, `T` (liste, `App.tab_picker`). Pas prises pendant la saisie d'un filtre, ni dans le formulaire de connexion.
- Barre d'onglets : visible seulement avec 2 onglets ou plus ; `fit_tabs` garde ceux qui entourent l'affiché et signale le reste par `‹` `›`.
- **Un serveur par onglet** (fait) : le serveur est une propriété de l'onglet. `App.server_name` est le serveur de l'onglet affiché (miroir, comme `stack`), `tab_servers` celui des autres (parallèle à `tabs`, mis à jour au départ de l'onglet par `go_tab`/`sync_server`). `S` ouvre la liste (`server_picker`) ; `switch_server` remplace la pile de **l'onglet affiché** par un `Home` neuf du nouveau serveur, les autres onglets ne bougent pas. Serveur déjà connecté (`caps` contient son nom) = bascule directe ; sinon le login s'ouvre avec `switch_to = true` et la bascule n'a lieu qu'au succès (`Échap` = onglet inchangé ; `login_escape` ne quitte que pour la connexion de démarrage).
- **Étiquetage des requêtes (point critique)** : deux serveurs peuvent avoir le même `owner/name` (mes instances de dev v15/v10 ont toutes les deux `smithy/secret`), donc sans étiquette une réponse irait dans les onglets de l'autre. Chaque `Request` est mise en file avec le serveur de l'onglet qui la demande (`queue`, `take_tagged_requests` ; ticks d'onglets en arrière-plan et explorateurs inactifs inclus), le canal de `main` porte `(serveur, Msg)` et `apply_for(serveur, msg)` ne diffuse qu'aux onglets de ce serveur (`stacks_of`) ; une réponse tardive après un changement est ignorée. `apply`/`take_requests` (sans étiquette) n'existent que pour les tests. Les requêtes d'un serveur sans fournisseur sont ré-empilées (`requeue`).
- **Gestion des serveurs depuis l'appli** : dans la liste `S`, `a` (ajout), `e` (modif : URL et token, **nom figé** car clé des sessions, de l'historique et des onglets ; token vide = inchangé), `d` + `y` (suppression ; refusée pour le dernier serveur et pour un serveur utilisé par un onglet). État pur dans `app.rs` (`ServerForm`, `ServerDraft`, `server_form_*`, `server_delete_*`) ; `main.rs` (`save_server`, `delete_server`) écrit la config **d'abord** (`config::save_servers`, réécriture complète au format `[[server]]`, 0600, commentaires perdus), puis met à jour le registre `Backend` et les capacités. Piège : la config en mémoire contient les surcharges `SMITHY_URL/TOKEN` ; on réécrit donc à partir du **fichier seul** (`config::file_servers`), en y ajoutant sans token les serveurs qui n'y sont pas (l'env-only `default`), pour ne jamais copier un secret d'environnement. `login_quits` : Échap sur un login ne quitte que si **aucun** serveur n'est connecté.
- **Premier lancement** : sans aucun serveur (ni fichier, ni `SMITHY_URL`), `config::load` renvoie une liste vide (plus d'erreur) et `run` ouvre `App::open_first_server_form` (`ServerForm.first_run`) : formulaire d'ajout imposé, sans liste `S` derrière, `server_form_escape` quitte. `save_server` reconnaît ce cas à `app.server_name` vide : `set_initial_server` donne au premier onglet le nouveau serveur (et réétiquette l'accueil déjà demandé), puis le login suit s'il n'y a pas de token. Vérifié en pty (rust:1-slim) : Échap n'écrit rien, la saisie écrit `config.toml` en 0600, la relance va droit au login.
- **Joignabilité vs session** : la liste `S` affiche deux états distincts. Réseau = `App.reach` (`Reach::{Checking, Up, Down(raison)}`), mesuré par `smithy_forgejo::ping` (`GET /api/v1/version` sans authentification, délais 4 s/5 s ; 401/403 comptent comme joignable, 404 = pas un Forgejo, 5xx = erreur HTTP) ; session = `is_connected` (fournisseur présent). L'état pur demande les sondes (`take_probes`, à l'ouverture de la liste puis à chaque `tick` tant qu'elle est ouverte), `main` les lance et renvoie `Msg::Reach{server,url,result}` ; une réponse pour une URL modifiée depuis est ignorée. Le résultat précédent reste affiché pendant la remesure.
- Capacités par serveur (`set_caps`, `is_connected`), resynchronisées à chaque changement d'onglet. `main.rs` tient un registre `Backend` par serveur (fournisseur, identifiant, token sauvegardé) ; au démarrage tous les serveurs qui ont des identifiants sont prêts, le serveur initial est `SMITHY_SERVER`, sinon le premier avec identifiants, sinon le premier (login). Une session expirée n'ouvre le login que si le serveur concerné est celui de l'onglet affiché.
- **Restauration des onglets** (`workspace.rs`, `~/.local/state/smithy/tabs.json`, 0600) : `App::snapshot()` capture pour chaque onglet son serveur et ses pages (`SavedPage` : Home{section,selected}, Repo, Runs, Browser{repo,branche,dossier}), `App::restore()` les rouvre et **redemande** les données avec les requêtes étiquetées du serveur de l'onglet (références seulement, jamais de contenu). Les **logs ne sont pas restaurés** (il faudrait le run entier) : l'onglet revient à la liste des runs. Un serveur disparu écarte son onglet ; une pile sans accueil ou une section hors bornes sont réparées. `main` réécrit le fichier dès que l'instantané change (pas à la fermeture : Ctrl+C ou plantage ne perdent rien). `--fresh` ne restaure pas (et le fichier est alors écrasé).
- **Une seule instance gère les onglets** : `workspace::acquire` prend un verrou de fichier (`File::try_lock`, std ≥ 1.89, d'où `rust-version = "1.89"` ; libéré par l'OS même après `kill -9`, pas de verrou périmé). Instance seconde (`Ownership::Other`) : un onglet vierge, rien restauré ni sauvegardé, avertissement en haut à droite (`App.shared_instance`). Verrou impossible (`Unavailable`) : pas de restauration, sans bruit. `recent.json` est **fusionné** à l'écriture (`recent::merge`, `save_merged`) pour que deux instances ne s'effacent pas. Piège de test : le pilote pty doit vider la sortie du TUI (sinon le TUI bloque sur l'écriture) et ne jamais lire « jusqu'à silence » (il redessine toutes les 100 ms).

## Souris et trackpad (`mouse.rs`)

- Capture activée dans `main` (`mouse_capture`, après `ratatui::init`) et retirée en sortant **et dans un crochet de panique** (`ratatui::init` ne restaure pas la souris : sinon le shell recevrait les séquences). Contrepartie : le terminal ne sélectionne plus le texte seul (Maj, ou Option sur iTerm2/Terminal.app).
- **Zones déposées par le rendu**, comme `viewport` : `App.zones` (`mouse::Zones`, `RefCell`) est vidé au début de `ui::draw`, chaque élément cliquable y dépose son rectangle et sa `Target` (`Tab`, `Section`, `Crumb(page)`, `Row`, `PickerRow`, `TextRow`, `Overlay`, `Outside`) ; la dernière déposée est au-dessus (`hit` cherche à l'envers). Les lignes d'une liste utilisent le **décalage après rendu** (`ts.offset()`) : `list_zone` (tableau encadré, une ligne d'en-tête), `picker_zone` (liste par-dessus : `Outside` plein écran = ferme comme Échap, cadre `Overlay` inerte, puis les lignes). Login et formulaire de serveur : `Overlay` plein écran, la souris n'y fait rien.
- `main::on_mouse` / `click` **réutilisent le clavier** : la frappe est sortie de la boucle dans `on_key`. Clic sur une ligne = `list_move(i - sélection)` ; sur la ligne déjà sélectionnée = `on_key(Enter)` (un double-clic revient au même). Listes par-dessus : `App::picker_selected`/`picker_move` (serveurs, onglets, branches de l'explorateur et de l'historique). Molette : liste par-dessus, sinon liste de la page (`list_selected` non vide), sinon `text_scroll(±3)`. Pas de clic de page pendant une saisie (`is_typing`).
- Fil d'Ariane : `App::breadcrumb_pages` donne pour chaque segment la page de la pile qui l'a ajouté (`None` = serveur → liste `S`), `mouse::crumb_sources` retrouve le segment derrière l'abrégé de `fit_breadcrumb` (« … ») ; `App::pop_to` dépile jusqu'à elle. `TabBar.first` donne l'indice réel des onglets affichés.
- Volet de texte : `TextView::click_row` plie/déplie la section dont le titre est sous le clic (ligne d'écran → `window()[row].line_no`).
- Vérifié en pty (pyte, séquences SGR `\x1b[<b;x;yM`) sur l'instance de dev : section, sélection puis ouverture, rubrique, molette, fil d'Ariane, capture retirée à la sortie.

## Accueil et page d'un dépôt (API REST, identique de la 10 à la 15)

`Page::Home` est le fond de la pile : cinq sections (`Section`) en titre du cadre, `←`/`→` pour changer, la courante en vidéo inverse. Sources (`RepoSource`) : **Mes dépôts** `/user/repos` (tout ce à quoi l'on a accès : les siens, organisations, collaborations), **Suivis** `/user/subscriptions`, **Étoilés** `/user/starred`, **Explorer** `/repos/search?q=…` (une seule page de 50, enveloppée dans `{"ok":true,"data":[…]}`, `data` peut être `null` : recherche à la demande, jamais « tout lister »), **Récents** : historique local, aucune API. Chaque ligne porte déjà description, privé/archivé/fork/vide, étoiles, PR ouvertes et date de mise à jour (`RepoInfo`) : aucune requête de plus. Seule la CI d'un dépôt se charge à l'ouverture de sa page.

- Les sections se chargent **à la première visite** ; `r` recharge la courante. `/` filtre localement (nom + description) ; dans Explorer c'est la requête envoyée au serveur. Le filtre est conservé quand on revient à l'accueil (Échap le retire).
- `RepoSource::Search` : une réponse pour une recherche abandonnée est ignorée (`HomeView::submitted`).
- La page d'un dépôt (`RepoView`) affiche la fiche (rechargée par `RepoInfo`) et propose **CI** (dernier run en résumé) et **Code** ; les futures rubriques (PR, runners…) s'y ajouteront.
- La liste des runs (`RunsView`) se rafraîchit toute seule ; la **sélection suit le même run** (par id) quand de nouveaux arrivent en tête. Une entrée de l'API est un **job** : `apply_pipelines` remet les jobs d'un même run (même `number`, consécutifs) dans l'ordre des ids croissants (déclaration du workflow ; l'API les donne décroissants) sans toucher à l'ordre des runs, et `pages::run_positions` (`RunPos`) dit à l'affichage comment les relier (`┌ ├ └`, colonnes Run et Job ; le reste du run n'est écrit que sur la première ligne). Calculé sur la liste **filtrée** : un run dont un seul job reste visible redevient une ligne simple.
- Organisations et notifications : `/user/orgs`, `/notifications`, `/repos/issues/search` répondent **403** avec les droits du token créé au login (`read:repository`, `read:user`) ; 200 avec `read:organization`, `read:notification`, `read:issue` (mesuré sur la 15). Non utilisés pour l'instant.
- Les listes de dépôts vides peuvent être `null` : toujours décoder en `Option<Vec<_>>`.

## Explorateur de code (API REST, identique de la 10 à la 15)

Contrairement aux logs, tout passe par l'API documentée avec le **token** (pas de cookie, pas d'adaptateur par version) : `GET /repos/{o}/{r}` (`default_branch`), `/branches` (page de 30 par défaut, **plafonnée à 50** ; total dans `x-total-count`), `/contents[/{chemin}]?ref=` (liste d'un dossier : tout en une réponse, 130 entrées vues, pas de plafond), `/raw/{chemin}?ref=` (octets, avec `Content-Length`). Mesuré avec `dev/dev.sh probe-browse` sur 10, 11, 12, 13, 14 et 15 : seuls des champs facultatifs d'une entrée varient. Points à retenir :
- **Dépôt sans commit** : `/branches` répond **`null`** (pas `[]`) et `/contents` une liste vide. `null` doit être décodé comme une liste vide (`Option<Vec<_>>`), sinon l'explorateur affiche « réponse inattendue » : bug trouvé par le test réel, pas par les tests unitaires.
- **Fichiers** : lire par `raw` en s'arrêtant au plafond (1 Mio, `FILE_LIMIT_BYTES`) ; `contents` renvoie tout le fichier en base64 sans plafond. Binaire = octet nul dans les 8 premiers Kio. Au plus 50 000 lignes affichées.
- **Chemins** : encoder chaque segment (`encode_path`) ; espaces, `#`, `?`, `%`, accents vérifiés. Une branche avec un `/` (`feature/x`) passe telle quelle en paramètre `ref`.
- Lien symbolique et sous-module : listés, jamais ouverts (non créables par l'API de dev, donc non testés en réel : seulement par tests unitaires).
- `ref` vide n'est jamais envoyé : on connaît d'abord la branche par défaut (liste des branches), puis on demande la racine.
- Touches : `e` depuis la liste des dépôts ; `B` ouvre le sélecteur de branche (pas `b`, déjà « page précédente » dans le volet de texte).

- **Coloration syntaxique** (`highlight.rs`) : syntect (`parsing` + `regex-fancy`, **pas d'onig**, vérifié par `cargo tree`) avec les grammaires de `two-face` (`extra_newlines` : TOML, TypeScript, Dockerfile… en plus du jeu par défaut). On **n'utilise pas de thème RGB** : les scopes sont classés en jetons (`Tok`, table `rules()` : de l'intérieur vers l'extérieur, première règle qui préfixe un scope) peints par `ui::tok_style` avec les 16 couleurs ANSI du terminal. Le jeu « newlines » exige une fin de ligne : `run` ajoute `\n` à chaque ligne (test d'un `//` suivi de code). Langage trouvé sans disque : nom de fichier (`Makefile`), extension, puis première ligne (shebang) ; « Plain Text » = pas de couleur. Garde-fous : > 20 000 lignes ou ligne > 1 000 octets = non colorée.
- **Hors du fil de l'interface** : `run_request` envoie `Msg::File` (texte tout de suite) puis, dans `spawn_blocking` (chargement des grammaires + analyse, plusieurs secondes en debug), un second message `Msg::FileStyles{repo,reference,path,fingerprint,styles}`. Les régions sont des décalages d'octets du texte **affiché** : `browser::file_lines` (nettoyage `clean_text_line` : tabulation = 4 espaces, contrôles = images Unicode) est partagé par l'affichage et l'analyse. `TextView::set_styles` refuse un résultat dont l'empreinte (`fingerprint_of`) ou le nombre de lignes ne correspondent plus (fichier rechargé entre-temps). `LogLine.runs` est vide pour un log. `Row` porte `offset` + `runs` ; `highlight::segments` découpe une ligne d'écran (retour à la ligne compris, via `wrap::ranges`).
- **Markdown** (`markdown.rs`, pulldown-cmark sans fonctionnalités par défaut ; options TABLES, STRIKETHROUGH, TASKLISTS, FOOTNOTES) : un `.md` s'ouvre **mis en forme** (`FileView.rendered`, vue `TextView` en plus de `text` = la source ; `FileView::view()` donne celle à l'écran, `m` bascule via `Browser::toggle_rendered`). `render` produit des `MdLine` (texte, régions, `hang`, `words`) : un paragraphe = **une** ligne logique, repliée **par mots** avec retrait des lignes suivantes (`wrap::layout(text, width, hang, words)`, `wrap::count` ≡ `layout().len()` par construction, testé) ; code et tableaux ne se replient qu'au caractère. Le texte rendu **ne dépend pas de la coloration** (`render(src, highlight_code)` ne change que les régions) : `on_file` rend tout de suite sans coloration, puis le `Msg::FileStyles` de la tâche de fond apporte `rendered: Option<(empreinte, régions par ligne)>` (blocs de code colorés par `highlight::highlight_as`), appliqué par `set_styles` si l'empreinte du texte rendu correspond. La vue rendue force `wrap = true` et `App::text_toggle_wrap` n'y touche pas (ne modifie pas `App.logs_wrap`). Liens : la cible est affichée après le texte ; images : `[image : alt] (url)` ; HTML brut estompé. `Mode::File` contient un `Box<FileView>` (clippy `large_enum_variant`).
- **Filtre des runs** (`RunsView` dans `pages.rs`) : `filter` (texte, mots en ET, sans casse, sur workflow/job/branche/commit/titre/`#numéro`/statut), `status: StatusFilter` (`s` : Tous → Échecs → Succès → En cours) et `editing`. `selected` est un indice dans `visible()` (la liste filtrée) : `selected_pipeline`, `move_selection`, `apply_pipelines` (qui garde le même run par id) et `open_logs` passent tous par elle. `Échap` : annule la saisie, sinon retire les filtres (`App::runs_clear_filters`), sinon retour. Touches dans `main::runs_key`. `App::is_typing()` (filtre de l'accueil, des runs, recherche) neutralise `t`/`x`/`Tab`/`S`.
- **Recherche dans un volet de texte** (`TextView`, logs + fichiers + rendu Markdown) : `/` ouvre `prompt`, `Entrée` calcule les occurrences (`Search`), `n`/`N` (`step_match`) bouclent. Casse « intelligente » (`textsearch::smart_case`). Les titres d'étape ne sont **pas** cherchés (habillage) ; une occurrence dans une étape pliée la déplie (`reveal_match`) et le défilement vise la ligne d'écran repliée qui contient le début de l'occurrence (`wrap::layout`). Le contenu qui change (log suivi, fichier rechargé) recompte et garde l'occurrence courante (`refresh_search`, appelé par `set_plain`/`set_log`/`set_lines`). `Row` porte `line_no` et la ligne entière pour que l'affichage retrouve les occurrences même à cheval sur deux lignes d'écran ; `textsearch::overlay` les superpose aux couleurs (vidéo inverse, jaune pour la courante). `Échap` : `App::text_escape` efface la recherche avant de laisser le retour se faire. Le pied de page (`search_line`) montre la saisie puis le bilan `n/N`.
- **Filtre par nom dans l'explorateur** (`Browser.filter` / `editing`, touche `/` dans un dossier chargé) : `visible()` (mots en ET, sans casse, sur le nom) ; `selected` est un indice dans `visible()` (enter, `len`/`move_selection`, rendu et compteur `n/m (sur total)` passent par elle). Le filtre est **propre à un dossier** : entrer dans un dossier, remonter ou changer de branche le retire (revenir d'un fichier au même dossier le garde, pour enchaîner les résultats). `Échap` : pendant la saisie il restaure le filtre validé d'avant (`filter_before`, aussi pour le filtre des runs), sinon il retire le filtre (`clear_filter`), sinon il ferme l'explorateur. `App::is_typing()` couvre aussi cette saisie.
- Piège de test : les couleurs sortent de crossterm en `38;5;N` (indexées), pas en `31`…`37` ; magenta = 5, vert = 2, gris = 8.

## Particularités de l'API Forgejo (décrites ici pour la 15 ; swagger de l'instance)

- Les runs viennent de `GET /repos/{o}/{r}/actions/tasks` (clé `workflow_runs`, un run par entrée = un job ; `run_number` est le numéro du run dans l'URL, distinct de `id`). Il n'existe **aucun endpoint REST de jobs ni de logs** dans le swagger.
- Les logs ne sont servis que par les **routes web internes** (non documentées, donc susceptibles de changer) : `POST /{o}/{r}/actions/runs/{run_number}/jobs/{index}/attempt/{n}` avec `{"logCursors":[{"step":0,"cursor":null,"expanded":true}]}`. Sans le segment `attempt/{n}`, `steps` reste vide sans erreur. `index` est la position du job dans `state.run.jobs`, pas son id. Les lignes contiennent des séquences ANSI et des `\r`. Une étape hors bornes dans `logCursors` fait répondre une page HTML d'erreur : lire d'abord la liste des étapes (appel sans curseur). Pas de pagination observée (6000 lignes en une réponse) ; un curseur `N` renvoie les lignes d'index > N. Procédure dans `smithy-forgejo/src/logs.rs` : liste des jobs → index → dernière tentative (`allAttempts`) → étapes → sortie.
- **Ces routes n'acceptent pas le token** : sur un dépôt privé, token et basic auth donnent 404 ; seul le cookie `session` passe (sur un dépôt public, tout passe, y compris sans auth : ne pas s'y fier pour tester l'auth). L'API `/api/v1` fait l'inverse (cookie seul = 401).
- Login (`smithy-forgejo/src/login.rs`) : `POST /user/login` (formulaire `user_name`, `password`, `remember=on`, sans CSRF sur Forgejo 15) → 303 si succès, 200 si échec ; le dernier `Set-Cookie: session` l'emporte. Le token en lecture seule est créé ensuite par `POST /api/v1/users/{login}/tokens` en basic auth. Le cookie `persistent` seul ne restaure pas la session : à l'expiration, il faut se reconnecter. Durée de vie de la session non mesurée. 2FA/SSO non gérés.
- Dans cette réponse, `name` est le nom du job et `workflow_id` le fichier de workflow ; `Pipeline.workflow` vient de `workflow_id`.
- Auth : en-tête `Authorization: token <t>`. Le token de dev est en lecture seule.

## Environnement de dev (`dev/`)

`dev/dev.sh` pilote un Forgejo jetable (SQLite) + un `forgejo-runner` dans Docker Compose : `up`, `seed` (pousse un workflow vert et un rouge sur `smithy/demo`, et un workflow riche — 2 jobs, ANSI, 250 lignes — sur le dépôt **privé** `smithy/secret`, plus les dépôts **privés sans workflow** `smithy/tree` — ~160 fichiers de test, 63 branches dont `feature/x` et `history` (60 commits : message multiligne, unicode, ajout+modif+suppression, binaire), un dossier `code/` (Rust, TOML, TS, JSON, Python, Dockerfile, un `.rs` de 1 Mio…) et `docs/rich.md` pour la coloration et le Markdown, un fichier de 1,5 Mio, un binaire, des noms avec espaces/`#`/`?`/accents — et `smithy/vide` sans commit, via `dev/seed-tree.py` ; idempotent), `reset` (`down -v`), `env`, `wait` (attend la fin des runs), `probe` (seed + `dev/probe-logs.py`, JSON des différences entre versions des routes de logs), `probe-browse` (idem pour l'API de contenu, `dev/probe-browse.py`), `probe-history` (idem pour commits, diff et branches, `dev/probe-history.py`), `probe-pulls` (API des pull requests, `dev/probe-pulls.py` ; fixtures `smithy/revue` par `dev/seed-pulls.py`). `FORGEJO_VERSION=N` lance une autre version **isolée** de la 15 (projet Compose `smithy-dev-vN`, port 3300+N, `dev/.env.vN.local`). Le token est écrit dans `dev/.env.local` (gitignoré). Forgejo écoute sur `127.0.0.1:3300` (15 par défaut).

- Le runner tourne en root avec le socket Docker de l'hôte : acceptable pour ce dev jetable uniquement.
- Les workflows de démo n'ont pas de `checkout` : les conteneurs de job ne joignent pas `localhost:3300`.
- **Les fixtures décalent les scénarios de test réels** : `history` est la dernière branche alphabétique, `code/` et `docs/` s'intercalent dans la racine de `main` ; les scénarios pilotés au clavier par indices (touches `j` répétées, `G` dans un sélecteur) sont à réajuster quand on ajoute des fixtures. Mettre l'historique sur une branche à part garde la racine de `main` stable.
- **Fixtures de l'explorateur : jamais dans `secret`** (ses workflows `on: [push]` se déclencheraient à chaque ajout et fausseraient `wait`), jamais par `git push`, et pas par `put_file_in` pour du gros ou du binaire (argument limité à 128 Kio, octets nuls perdus) : `seed-tree.py` utilise l'API de contenu multi-fichiers.
- Ne pas lancer de `docker pull` interrompu/répété pendant qu'un autre tourne : le démon peut rester bloqué (observé une fois : `docker ps` ne répondait plus alors que les conteneurs tournaient ; je n'ai pas vérifié ce qui le débloque).
- Un `docker compose up` sans token de runner fait crasher le service `runner` ; `dev.sh` démarre donc `forgejo` seul d'abord, puis le runner avec le token.

## CI et releases (`.github/workflows/`)

Le dépôt est sur GitHub : deux workflows GitHub Actions, sur le modèle de `lazyshell`. **Je n'ai pas accès aux runs** (pas de `gh` ni de réseau GitHub ici : leur résultat est à demander à Thomas) ; la compilation musl a été rejouée à la main dans `debian:bookworm-slim`, le report de version dans `rust:1-slim`, `actionlint` passe.
- `ci.yml` (nom `CI` : `release.yml` s'y accroche, ne pas le renommer ; push sur `main`, pull requests) : `cargo fmt --check`, `clippy -D warnings`, `cargo test`, tous `--locked`, comme `make check`.
- `release.yml`, trois entrées : (1) **CI verte sur `main`** (`workflow_run`, push seulement) → job `tag` : `.github/scripts/next-version.sh` (copie de lazyshell) calcule la version depuis le dernier tag `v*` selon Conventional Commits (`feat` mineure, `fix`/`perf`/`refactor` corrective, `!`/`BREAKING CHANGE` majeure, rien sinon ; sans tag on part de 0.0.0, donc premier `feat` = `v0.1.0`), pose et pousse le tag ; (2) tag `vX.Y.Z` poussé à la main ; (3) lancement manuel = archives en artefacts, pas de release. Tag et release dans le même workflow : un tag poussé avec `GITHUB_TOKEN` ne déclenche pas d'autre workflow.
- **La version vient du tag, pas du `Cargo.toml`** (qui reste à `0.1.0` dans le dépôt) : le job réécrit la version du `[workspace.package]` sur le runner puis `cargo update --workspace`, qui ne change que les 3 crates du workspace dans `Cargo.lock` (vérifié) : `--locked` reste valable, et `--version`/User-Agent donnent la vraie version (contrôlé par le job).
- Matrice `build` : `linux_amd64` (`x86_64-unknown-linux-musl`, ubuntu-latest), `linux_arm64` (`aarch64-unknown-linux-musl`, runner natif `ubuntu-24.04-arm`), `darwin_arm64` (macos-latest), `darwin_amd64` (croisé depuis macos-latest : ni tests ni lancement). Linux statique vérifié par `ldd`. Binaires *strip* (`CARGO_PROFILE_RELEASE_STRIP`). Archives `smithy_<os>_<arch>.tar.gz` (binaire `smithy` à la racine + README + licences) et un `checksums.txt` ; job `publish` → `gh release create --generate-notes`. Noms stables : `releases/latest/download/smithy_<os>_<arch>.tar.gz`, utilisé par `scripts/install.sh` (curl | bash, vérifie la somme avec `sha256sum` ou `shasum`, installe dans `/usr/local/bin` ou `$SMITHY_INSTALL_DIR` ; testé localement avec des URL `file://`).
- Pourquoi musl : machine cible sans bureau, distribution inconnue ; un binaire glibc dépendrait de la version de la libc. `ring` compile du C : il faut `musl-tools` et `CC_<cible>=musl-gcc`. Rustls seulement (pas d'OpenSSL), donc rien d'autre à lier.
- Rejouer en local sans installer musl : un conteneur Debian (`apt install build-essential musl-tools`, rustup, `cargo build --release --locked -p smithy --target x86_64-unknown-linux-musl`) donne un binaire statique de ~12 Mo.
- Pas encore : Windows, publication sur crates.io, signature des binaires, commande `smithy update`.

## Conventions

- Lints workspace : `unsafe_code = "forbid"`, clippy en `warn` (`-D warnings` via `make lint`).
- `rustls` uniquement (pas d'OpenSSL) pour que le binaire tourne sur une machine sans bureau.
- Le `README.md` (anglais) est à tenir à jour à chaque évolution visible : fonctionnalités, raccourcis, config, backends supportés, roadmap.
